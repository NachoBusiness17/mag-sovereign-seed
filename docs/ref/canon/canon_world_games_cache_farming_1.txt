2. The Cache Farming Loop for Prompts
Just as the RIB measures a model's behavior at the deterministic-stochastic boundary, a cache-farmed game prompt is a deterministic structure designed to produce a stochastic output. The farming loop is:

Design the Deterministic Map: Create the prompt's core mechanics and rule ordering. This is the stable prefix that will hit the cache.

Parameterize the Variable Content: Define the "fill-in-the-blank" sections for themes, cultural elements, and specific game rules. These are the stochastic variables that change per request .

Run the Measurement Probe: For each game variant, run the prompt (e.g., "Generate a Mancala variant with West African themes").

Generate the Receipt: Record the prompt hash, the generated game rules, the cultural accuracy score, and the cost.

Update the Atlas: Add the new prompt variant and its measured behavior to your library.

2. DESCRIBE IN 1 PARAGRAPH → Core loop + win condition (be specific about what, vague about numbers)
3. RUN IMMEDIATELY        → Play for 2 minutes; notice what's broken
4. TUNE WITH SMALL PROMPTS → One change at a time, in plain feel-words: "snappier, faster, more dangerous"
Why this matters for caching: Each iteration reuses the cached system prompt and tool definitions. Only the incremental tuning instruction (a few dozen tokens) is processed fresh.

IV. A Unified Framework: Cache-Optimized Game Prompt Engineering
4.1 The Multi-Layer Cache Strategy
text
┌─────────────────────────────────────────────────────────────┐
│ LAYER 1: System Prompt Cache (shared across ALL games)     │
│ → Role definition + output format + constraints            │
│ → Cache hit: ~400-500 tokens saved per request            │
├─────────────────────────────────────────────────────────────┤
│ LAYER 2: Genre Template Cache (shared within game type)    │
│ → Board logic / card logic / dice mechanics               │
│ → Cache hit: ~200-300 tokens saved per request            │
├─────────────────────────────────────────────────────────────┤
│ LAYER 3: Parameterized Instance Cache (per game variant)   │
│ → "Snake_20x20_neon" vs "Snake_15x15_retro"              │
│ → Semantic caching: structurally similar = cache reuse    │
├─────────────────────────────────────────────────────────────┤
│ LAYER 4: Generated Asset Cache (per type + prompt + seed)  │
│ → Sprites / backgrounds / sound effects                   │
│ → One generation, infinite reuse                           │
└─────────────────────────────────────────────────────────────┘

4.3 The Economics of Scale
For a production game generation service:

Each uncached generation: ~5,000 tokens

Each cached generation: ~500 dynamic tokens

77% token reduction per generation loop

For 1,000 game generations per day: ~4.5M tokens saved daily

V. Conclusion: The Prompt Genome as Infrastructure
The 2026 state of game prompt engineering reveals a mature discipline built on three pillars:

Structured prompt genomes that separate stable prefixes from variable parameters

Multi-layer caching from exact-prefix through semantic to generative caching

Iterative workflows that leverage cached context while tuning incrementally

The Core Law: The prompt genome tells us how to generate the game, what outputs to expect, and how to optimize for cost and latency. It does not claim to contain the game itself—the game code stays in the artifact layer until requested.

The field has moved from "vibe coding" to engineered prompt genomics—a shift from hoping for magic to designing reproducible, cacheable, economically-viable game generation systems.
